# 헤더 "알림"/"메시지" 배지 연동

> 최종 수정: 2026-08-17
> 대상: `04_gh_registry_api` (백엔드) + `04_gh_registry_front` (프론트, 파일 경로만 명시)
> 관련: `02_gh_admin_api/database/migrations/2026_08_12_000001_create_gh_notice_v4_tables.php` — "교회로 공지 센터"(`gh_notice_v4*`) 스키마 원본(02_gh_admin_api 소유, 이 저장소는 마이그레이션을 쓰지 않으므로 참고용 링크가 아니라 실제 소스 위치)

---

## 배경

헤더 우측 상단(`HeaderGnb.jsx`)의 "메시지"/"알림" 드롭다운은 원래 배지 숫자("3")와 목록 내용이 전부 하드코딩된 정적 mock이었다. 두 드롭다운을 조사한 결과 성격이 완전히 달라 처리 방향도 다르게 잡았다.

| 드롭다운 | 실데이터 소스 | 처리 |
|---|---|---|
| 알림 (벨) | 이미 구축되어 있던 "교회로 공지 센터"(`gh_notice_v4*`, 아래 1절 참고)와 항목이 거의 그대로 겹침 | **실연동** |
| 메시지 | "최근 상담 N건"이 가리키는 "상담" 개념 자체가 이 시스템 어디에도 없음(문자발송은 관리자→교인 발송 기록일 뿐, 인바운드 "상담 요청"이나 안읽음 추적 API가 없음) | 배지·가짜 목록 제거, 실제 동작하는 바로가기 링크만 유지 |

---

## 1. 데이터 구조 — `gh_notice_v4*` (스키마 소유권 주의)

- `gh_notice_v4` / `gh_notice_v4_resource` / `gh_notice_v4_read` 세 테이블은 **02_gh_admin_api(플랫폼 관리자)가 작성한 마이그레이션 소유**다. 같은 물리 DB를 공유하는 기존 테이블이라 이 저장소에서 스키마를 건드리지 않는다(CLAUDE.md 절대금지 사항).
- 교적(`04_gh_registry_api`)은 **읽기 전용**으로 `gh_notice_v4`/`gh_notice_v4_resource`를 조회하고, 유일한 write는 `gh_notice_v4_read`(교적 관리자별 읽음 기록) 행 삽입/갱신뿐이다.
- 담당 클래스: [`NoticeRepository`](../app/Repositories/NoticeRepository.php) / [`NoticeService`](../app/Services/NoticeService.php) / [`NoticeController`](../app/Http/Controllers/Api/NoticeController.php)
- 라우트: `v4/notice/getList` / `getDetail` / `getResourceList` (`jwt.auth`만 요구 — 전 역할 공통 노출이라 도메인 권한 불필요)

`gh_notice_v4` 주요 컬럼: `notice_no`, `type`(`notice`/`update`/`check`/`guide`), `title`, `summary`, `content`, `is_pinned`, `status`(`ACTIVE`/`INACTIVE`), `is_deleted`.
`gh_notice_v4_read` 주요 컬럼: `notice_no`, `church_admin_no`(교적 관리자 — `gh_church_admin.admin_no`, **`gh_notice_v4.created_admin_no`(플랫폼 관리자)와는 다른 identity space**), `read_at`.

## 2. 안읽음 개수(배지) 계산 원리

새 엔드포인트를 만들지 않았다 — 기존 `getList`가 이미 필요한 걸 다 갖고 있었다.

```php
// NoticeRepository::getList()
SELECT n.notice_no, n.type, n.title, n.summary, n.is_pinned, n.created_at,
       (r.read_no IS NOT NULL) AS is_read
FROM gh_notice_v4 n
LEFT JOIN gh_notice_v4_read r
    ON r.notice_no = n.notice_no AND r.church_admin_no = ?   -- 요청자 본인 것만
WHERE n.is_deleted = 0 AND n.status = 'ACTIVE'
ORDER BY n.is_pinned DESC, n.notice_no DESC
```

응답의 각 항목에 이미 `is_read`(0/1)가 포함되므로, **안읽음 개수는 프론트에서 `list.filter(n => !n.is_read).length`로 계산**한다. 별도의 "unreadCount API"는 없다.

### 프론트 — 캐싱 방식

`PermissionContext`/`OrganizationContext`와 동일한 패턴: **로그인 세션당 `getList()` 1회만 호출**해 Context에 캐시하고, 페이지 이동마다 재조회하지 않는다.

- 파일: `04_gh_registry_front/src/context/NoticeContext.jsx` (신규)
- `main.jsx`에 `NoticeProvider`로 최상위에 wiring (`AuthProvider` → `PermissionProvider` → `OrganizationProvider` → `NoticeProvider` → `App`)
- 노출 값: `list`(전체), `recent`(최근 3건, 헤더 드롭다운 미리보기용), `unreadCount`, `markReadLocally(noticeNo)`

```js
// NoticeContext.jsx 핵심
const unreadCount = list.filter((n) => !n.is_read).length
const recent = list.slice(0, 3)
```

헤더(`HeaderGnb.jsx`)의 "알림" 버튼은 `unreadCount > 0`일 때만 배지를 표시하고(0이면 배지 자체를 숨김), 10개 이상이면 "9+"로 표기한다.

## 3. 읽음 처리 흐름

### 서버 — 상세 조회 시 자동 읽음 처리

```php
// NoticeService::getNoticeDetail()
$this->noticeRepository->markRead($noticeNo, $churchAdminNo);
```

```php
// NoticeRepository::markRead()
DB::table('gh_notice_v4_read')->updateOrInsert(
    ['notice_no' => $noticeNo, 'church_admin_no' => $churchAdminNo],
    ['read_at' => now()]
);
```

별도의 "읽음 처리" 버튼/엔드포인트가 없다 — **공지 상세를 조회하는 행위 자체가 곧 읽음 처리**다(`updateOrInsert`라 여러 번 열람해도 안전하게 upsert됨). 조회(GET) 액션이라 CLAUDE.md의 "조회에는 audit 안 함" 원칙과 동일하게 `reg_audit_logs`에는 남기지 않는다.

### 프론트 — 새로고침 없이 배지 즉시 갱신

상세 페이지가 `getNoticeDetail()`을 호출하면 서버에는 이미 읽음 기록이 남지만, **헤더는 이미 캐시된 목록을 들고 있어서 자동으로는 갱신되지 않는다.** 이를 위해 재조회 없이 로컬 캐시만 갱신하는 함수를 뒀다:

```js
// NoticeContext.jsx
const markReadLocally = useCallback((noticeNo) => {
  setList((prev) => prev.map((n) =>
    Number(n.notice_no) === Number(noticeNo) ? { ...n, is_read: true } : n
  ))
}, [])
```

`04_gh_registry_front/src/pages/platform/NoticeDetail.jsx`가 `getNoticeDetail()` 성공 직후 이걸 호출한다:

```js
getNoticeDetail(noticeNo)
  .then((d) => { setData(d); markReadLocally(noticeNo); })
  ...
```

`HeaderGnb.jsx`와 `NoticeDetail.jsx`가 같은 `NoticeContext`를 구독하므로, 상세 페이지를 여는 즉시(페이지 새로고침 없이) 헤더 배지 숫자가 줄어든다.

## 4. "메시지" 드롭다운 — 실데이터 없어 배지 제거

`04_gh_registry_front/src/layouts/HeaderGnb.jsx`에서 처리:

- 배지(`<b>3</b>`)와 "최근 상담 3건" 가짜 목록 항목 삭제
- 실제로 존재하는 화면 3개로 대체: 문자 발송(`/member/messaging`) / 단체 문자 보내기(`/member/messaging/compose`) / 발송 이력 보기(`/member/messaging/log`)
- 훗날 "인바운드 상담/문의" 같은 실제 개념이 생기면(예: 공개 홈페이지 "상담신청" 게시판을 관리자가 확인하는 흐름 등) 그때 안읽음 배지를 다시 붙이는 걸 검토

## 6. 검증 이력

2026-08-17, 로컬 dev DB(church_id=33632, test111 계정)에 테스트 공지 3건(업데이트/점검/일반, 고정 1건 포함)을 직접 INSERT해 브라우저로 검증:

- 최초 배지 "3" 정상 표시, 드롭다운에 고정글 우선 + `notice_no` 내림차순으로 3건 실데이터(제목/요약/작성시각) 렌더링 확인
- 공지 1건 상세 진입 → `gh_notice_v4_read`에 실제 읽음 기록 생성 확인(DB 직접 조회)
- 페이지 재진입 시 배지 "2"로 정확히 갱신, 읽은 항목엔 안읽음 표시(●)가 빠지는 것까지 확인
- 검증에 사용한 테스트 공지·읽음 기록은 전부 정리 완료(운영 데이터 없음)
