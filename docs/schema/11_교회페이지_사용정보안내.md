# ① 예배·모임 안내 (WorshipMeeting.jsx)

## 사용 테이블

| 테이블 | 사용 방식 |
|---|---|
| `gh_church_timetable` | **주 테이블** — 조회/등록/수정/삭제 전부 이 테이블 하나로 처리 |
| `reg_organizations` | **조건부·검증 전용** — `target_org_id`를 입력했을 때만 "이 조직이 실제 존재하고 같은 교회 소속인지" 확인 목적으로 1건 조회. **현재 `WorshipMeeting.jsx`/`교직설정 > 예배 기준` 어느 화면에도 `target_org_id`를 입력하는 UI가 없어 실질적으로 호출되지 않음** — 컬럼과 검증 로직만 존재 |

그 외 테이블은 사용하지 않음. (`WorshipService`에 `MemberRepository`가 주입되어 있었으나 실제로는 아무 메서드도
호출하지 않는 죽은 코드였음 — 이번에 확인하면서 제거함.)

## gh_church_timetable 컬럼 매핑

| 필드 | 컬럼 | 비고 |
|---|---|---|
| 예배명 | `name` | |
| 설명 | `description` | VARCHAR(200), 이번 기능 추가 시 신규 컬럼(원래 교직설정 탭엔 없던 필드) |
| 비고 | `note` | VARCHAR(200), 위와 동일하게 신규 |
| 요일 | `day_of_week` | TINYINT, 0=일~6=토, NULL=매일 |
| 시간 | `start_time` | TIME, NULL 가능 |
| 분류 | `category` | `regular`(정기) / `other`(기타), 기본값 `regular` |
| 대상 조직 | `target_org_id` | `reg_organizations.id` 참조, 현재 UI 미노출(위 참조) |
| 정렬 순서 | `sort_order` | |
| 활성 여부 | `is_active` | 삭제는 hard delete가 아니라 `is_active=0`(soft) |

## API / 쿼리

| 액션 | 엔드포인트 | 쿼리 |
|---|---|---|
| 목록 조회 | `POST /v4/worship/getList` | `SELECT ... FROM gh_church_timetable WHERE church_no = ? [AND is_active/day_of_week/keyword 필터]` |
| 상세 조회 | `POST /v4/worship/getDetail` | `SELECT ... FROM gh_church_timetable WHERE timetable_no = ?` |
| 등록 | `POST /v4/worship/register` | `INSERT INTO gh_church_timetable (...)` (+ `target_org_id` 있으면 `reg_organizations` 존재 검증) |
| 수정 | `POST /v4/worship/update` | `UPDATE gh_church_timetable SET ... WHERE timetable_no = ?` |
| 삭제 | `POST /v4/worship/delete` | `UPDATE gh_church_timetable SET is_active = 0 WHERE timetable_no = ?` (soft) |

Controller/Service/Repository: `WorshipController` / `WorshipService` / `WorshipRepository`
(`app/Http/Controllers/Api/`, `app/Services/`, `app/Repositories/`).

## 이 API를 공유하는 화면이 2개

`v4/worship/*`는 **`WorshipMeeting.jsx`(관리 > 교회 페이지 > 예배안내)와 교직설정 > 예배 기준 탭
(`MemberSettings.jsx`의 `WorshipCriteria`) 둘 다 사용**하는 완전히 동일한 API. 화면은 2개, 백엔드는 1개.

- `교직설정 > 예배 기준`: 행 하나 = 예배 하나(단순 리스트, 시간 1개, 설명/비고 편집 UI 없음)
- `WorshipMeeting.jsx`: 같은 데이터를 "카드" 단위로 다시 묶어서 보여줌 — **`name`이 같은 행 여러 개를
  하나의 카드**로 그룹핑(카드 = 예배명 + 여러 시간). 카드에서 "시간 추가"를 누르면 실제로는
  `gh_church_timetable`에 새 행 하나가 더 생기는 구조(같은 이름, 다른 `start_time`).
  저장 시 프론트에서 기존/신규/삭제된 시간을 구분해 `register`/`update`/`delete`로 나눠 호출.

## 교회 기본정보 (ChurchInfoSection)

| 필드 | 테이블.컬럼 | 담당 서비스 |
|---|---|---|
| 창립 년도 | `gh_church.church_create_date` | ChurchProfileService |
| 표어 | `gh_church_intro.slogan` | IntroService |
| 교회소개 제목 | `gh_church_intro.intro_title` | IntroService |
| 비전 | `gh_church_intro.vision` | IntroService |
| 주소/상세주소/우편번호 | `gh_church_location.address` / `address_detail` / `postcode` | ChurchProfileService |
| 시/도·시/군/구·동·좌표 | `gh_church_location.sido_no` / `sigungu_no` / `dong_no` / `latitude` / `longitude` | ChurchProfileService (주소 변경 시 `RegionMatcher`+`GeocodeHelper`로 자동 재계산) |
| 연락처 | `gh_church.phone` | ChurchProfileService |
| 이메일 | `gh_church.email` | ChurchProfileService |
| 홈페이지 URL | `gh_church.homepage` | ChurchProfileService |

**두 서비스로 나뉘어 있는 이유**: 주소/연락처/이메일/홈페이지/창립년도는 설정 > 교회 프로필(`ChurchProfile.jsx`)이 이미
관리하는 동일한 사실이라 새로 만들지 않고 그대로 재사용 — 프론트도 `churchProfileService.js`(`getProfile`/`updateProfile`)를
그대로 호출. 표어/교회소개제목/비전만 교회소개 전용이라 `introService.js`(`updateIntro`)로 별도 저장.

- 조회: `GET` 은 없고 페이지 로드 시 `getProfile()` + `getIntro()` 두 번 호출해 하나의 화면에 합쳐 표시
  - `ChurchProfileRepository::getChurch()` → `SELECT ... FROM gh_church WHERE church_no = ?`
  - `ChurchProfileRepository::getLocation()` → `SELECT ... FROM gh_church_location WHERE church_no = ?`
- 저장(주소/연락처 등): `POST /v4/churchProfile/updateProfile` → `ChurchProfileService::updateProfile()`
  - `UPDATE gh_church SET ... WHERE church_no = ?` (연락처/이메일/홈페이지/창립년도)
  - 주소 변경 시(주소 검색 모달을 실제로 써서 `sido_name` 등이 함께 온 경우에만) `RegionMatcher::match()`(시/도·시/군/구·동 이름 → `gh_sido`/`gh_sigungu`/`gh_dong` 테이블 조회로 번호 매칭) + `GeocodeHelper::getCoordinatesFromAddress()`(카카오 로컬 API 호출)로 좌표 재계산 후 `ChurchProfileRepository::upsertLocation()` → `gh_church_location` UPDATE/INSERT
- 저장(표어/제목/비전): `POST /v4/intro/updateIntro` → 위 요약과 동일 경로(`upsertIntro`)

## 목회자 소개 (PastorSection)

| 필드 | 테이블.컬럼 |
|---|---|
| 이름 | `gh_church_pastor.name` |
| 직함 | `gh_church_pastor.type_no` (FK → `gh_church_pastor_type.type_no`) |
| 주요 약력(다건) | `gh_church_pastor.career` (TEXT, JSON 문자열 배열) |
| 사진 | `gh_church_pastor.thumbnail` (FK → `gh_file.file_no`) |

- 대상 목회자: **담임목사만**(`is_head = 1`인 행). 지정 자체는 이 화면이 아니라 설정 > 교회 프로필에서 함
  (`ChurchProfileService::setHeadPastor` — 이 화면은 몰라도 됨, 조회만).
- 조회: `IntroRepository::getHeadPastor()` → `SELECT * FROM gh_church_pastor WHERE church_no = ? AND is_head = 1`,
  직함 목록은 `IntroRepository::getPastorTypes()` → `SELECT * FROM gh_church_pastor_type`,
  사진은 `IntroRepository::getFileByNo()` → `SELECT * FROM gh_file WHERE file_no = ?`
- 저장(이름/직함/약력): `POST /v4/intro/updatePastor` → `IntroService::updatePastor()` →
  `UPDATE gh_church_pastor SET name=?, type_no=?, career=? WHERE pastor_no = ?`
- 사진 업로드: `POST /v4/intro/uploadPastorPhoto`(multipart) → `IntroService::uploadPastorPhoto()` →
  `S3FileHelper::upload()`로 S3 업로드 → `INSERT INTO gh_file`(신규 file_no) → `UPDATE gh_church_pastor SET thumbnail = ?`
  → 기존 사진 있었으면 `UPDATE gh_file SET status='DEAD'` + S3에서 실제 삭제
- 사진 삭제: `POST /v4/intro/deletePastorPhoto` → 위 업로드의 역방향(thumbnail을 NULL로, 기존 파일 DEAD 처리 + S3 삭제)
